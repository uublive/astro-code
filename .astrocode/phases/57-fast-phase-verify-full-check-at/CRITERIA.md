# Criteria — phase 57: Fast phase verify, full check at milestone close

> Pre-registered, plan-blind (ADR-021). Derived from the phase goal, CONTEXT.md decisions 1-8 and
> ADR-094 (amends ADR-079/089/091/093). "Scratch project" below means a throwaway git repo under
> the temp dir initialised with `ac init`, with a milestone and phases created through `ac` verbs,
> a project test command whose runs are observable (e.g. each test file / the suite runner appends a
> line to a log file outside the repo), and phase work committed with ADR-017 stamps. The verifier
> builds it with Bash; no network is needed.

### C1 [core] — With no setting at all, a project verifies phases in fast mode: the phase verify paths never run the full test suite
- **Observe:** In a fresh scratch project (no verify setting in `.astrocode/config.json`), give a phase a criterion with a `Cheap:` command and a stamped commit changing one source file that one test file covers; make the full suite command observable (it appends `SUITE` to a log). Run `ac verdict cheap <phase> --json` (and any other verify gate verb the fast path uses, e.g. `ac verdict plan <phase> --json`). Expected: the log shows no `SUITE` run, the covering test file did run, the JSON/output states the fast mode and the targeted set. Also read the verifier contract as rendered for a fast-mode project (`workflows/execute-phase.mjs` verifier prompt, `commands/astro-verify.md`, `agents/astro-verifier.md`): it directs the verifier to the targeted set and not the full suite. Files: `bin/ac.mjs`, `lib/verdict.mjs`, `lib/config.mjs`, `workflows/execute-phase.mjs`, `commands/astro-verify.md`, `agents/astro-verifier.md`.
- **Fails if:** the default (unset) mode is `phase`/full-suite; the cheap pass still runs or demands a suite receipt in fast mode; or any verifier instruction path in fast mode still tells the verifier to run the whole suite (e.g. only the workflow tier was changed and the inline `/astro-verify` tier still runs `npm test`).

### C2 [core] — Remediation in fast mode is also held to the targeted set, never the full suite
- **Observe:** Read the remediation/heal executor instructions as the execute-phase workflow builds them for a fast-mode project (`workflows/execute-phase.mjs`, and the remediation path of `commands/astro-verify.md` / `commands/astro-execute.md`); if the prompt builder is exported or testable, render it with fast mode on and off (`node -e` importing the builder, or the workflow's own test in `tests/workflows.test.mjs`). Expected: with fast mode on, the remediation executor is told to run the phase's targeted tests (or the affected tests) and not the full suite; with the per-phase setting it keeps today's instruction.
- **Fails if:** a remediation executor in fast mode is still instructed to run the full suite (or "all tests") before committing, so a remediation round still pays the suite cost the goal removes.

### C3 [core] — The targeted test set is computed in code, deterministically: the phase's changed test files plus the tests of the source files it changed, and nothing unrelated
- **Observe:** In a scratch project with `src/a.mjs`, `src/b.mjs`, `tests/a.test.mjs` (imports `src/a.mjs`), `tests/b.test.mjs` (imports `src/b.mjs`), `tests/c.test.mjs` (imports neither), commit as the phase (stamped) a change to `src/a.mjs` and a new/changed `tests/d.test.mjs`. Ask the verb that reports the phase's targeted set (e.g. `ac verdict cheap <phase> --json` or `ac verdict plan <phase> --json`) twice. Expected: the set is exactly `tests/a.test.mjs` + `tests/d.test.mjs` both times (same order), `tests/b.test.mjs` and `tests/c.test.mjs` excluded; the report states the selection's limits. Changes made by commits outside the phase (unstamped or another phase's stamp) do not enter the set. Files: `lib/verdict.mjs`, `bin/ac.mjs`.
- **Fails if:** the set is chosen by the verifier/agent rather than returned by code; it misses the test that imports a changed source file; it includes unrelated tests or other phases' changes; or two runs on the same tree give different sets.

### C4 [core] — A phase with no linked tests runs no tests, says "no linked tests", and does not fall back to the full suite
- **Observe:** In a fast-mode scratch project, a phase whose stamped commits touch only docs/prompt files (e.g. `README.md`, `commands/x.md`) that no test imports or names. Run `ac verdict cheap <phase>` (and `--json`). Expected: no test file and no suite runs (log empty), the output says "no linked tests", only the criteria's `Cheap:` commands run, and a PASS verdict for that phase can be recorded with `ac verdict record` without any test evidence. Files: `lib/verdict.mjs`, `bin/ac.mjs`.
- **Fails if:** an empty targeted set triggers the full suite; the report is silent or claims tests passed; or the PASS gate refuses the phase because no tests ran.

### C5 [core] — A fast-mode PASS is accepted only when the targeted set is green on the verified commit; a red or stale targeted run is refused in code
- **Observe:** In a fast-mode scratch project, make the targeted test for the phase fail at HEAD, then try `ac verdict record <phase> --result '<PASS json>'` and `ac phase verify <phase>`. Expected: both refuse with a message naming the failing targeted test(s). Fix the test, commit, re-run the cheap pass, record PASS: accepted with no full-suite evidence demanded. Then add a new commit changing a covered source file without re-running the targeted set and try to record PASS at the new HEAD: refused (evidence is for another commit). Files: `lib/verdict.mjs`, `bin/ac.mjs`.
- **Fails if:** a PASS is recorded while the targeted tests fail or were run on a different commit; the gate is only verifier prose and `ac verdict record` accepts the PASS; or the fast-mode gate still demands a full-suite receipt.

### C6 [core] — A project setting restores today's per-phase full-suite behaviour, and in that mode nothing is pending or gated
- **Observe:** Read the setting's name in `MANUAL.md` / `commands/astro-config.md`, set it to the per-phase value in a scratch project's `.astrocode/config.json` (through `ac` if a config verb exists). Run `ac verdict cheap <phase>`: the full suite runs (or is held back as slow per ADR-093) exactly as before, and a PASS still needs the full suite on the verified commit (`ac verdict record` refuses a PASS without it). After verifying/accepting every phase in this mode, `ac status` shows no "full check pending" marker and `ac milestone complete` is not blocked for lack of a milestone full check. Files: `lib/config.mjs`, `lib/verdict.mjs`, `lib/milestone.mjs`, `bin/ac.mjs`.
- **Fails if:** the setting is ignored (fast mode still applies); in per-phase mode the full-suite PASS requirement is lost; or per-phase projects get the pending marker or the milestone-close gate they never had.

### C7 [core] — A fast-verified phase is visibly marked "fast-verified, full check pending" everywhere a human looks, while still verifiable, acceptable and releasable
- **Observe:** In a fast-mode scratch project, verify a phase (C5 path), then run `ac status`, `ac phase show <phase>`, the band/statusline output (`hooks/` statusline or band renderer run with the project as cwd), and `ac phase accept <phase>` (`--agent test`). Expected: the phase reaches verified and is accepted without a full check, and each of these outputs says "full check pending" (or equivalent wording naming the pending full check) for that phase. After a passing milestone full check (C8) on the current tip, the marker is gone from `ac status`. Files: `bin/ac.mjs`, `lib/status.mjs`, `hooks/`, `lib/phase.mjs`.
- **Fails if:** a fast-verified phase reads identically to a fully checked one in any of status, band, phase show or accept output; the marker survives a passing full check; or accept/verify is refused merely because the full check is pending.

### C8 [core] — One command runs the milestone full check on the milestone tip: the full suite plus every phase's `Cheap:` re-checks, and only those
- **Observe:** In a scratch project with a milestone of three phases — P1 with two criteria carrying `Cheap:` commands, P2 with one, P3 with none — where each `Cheap:` command appends `<phase>:<criterion>:$(git rev-parse HEAD)` to a log outside the repo and the suite appends `SUITE:<sha>`. Run the milestone full-check command (e.g. `ac milestone verify`, as documented in `MANUAL.md`). Expected: the log shows exactly one suite run and the three `Cheap:` commands, all at the milestone tip SHA; P3 contributes nothing; no verifier agent re-verification of each phase is started; exit 0 and a report naming the tip commit and PASS. Files: `bin/ac.mjs`, `lib/milestone.mjs`, `lib/verdict.mjs`.
- **Fails if:** the suite or any phase's cheap re-check is skipped; checks run on a commit other than the tip; a phase with no `Cheap:` lines makes the check fail or run something extra; or the command requires a full per-phase re-verify.

### C9 [core] — A failing full check opens fixes tied to the responsible phase (criterion failures to their phase; suite failures to the phase that last changed the failing test's subject, else the milestone)
- **Observe:** Continue C8's scratch project: make P2's `Cheap:` command fail, and break a test whose subject file was last changed by P1's stamped commit; also break a test whose subject no phase changed. Run the full check. Expected: non-zero exit, `ac fix list` (`--json`) shows a fix tied to P2 for the criterion (its failing command and output pre-filled), a fix tied to P1 for the first suite failure, and a fix tied to the milestone (no phase) for the second. Re-running the check while those failures persist does not duplicate the fixes. Files: `bin/ac.mjs`, `lib/milestone.mjs`, `lib/fix.mjs`.
- **Fails if:** a failure opens no fix; every fix is tied to the milestone (or to the last phase) regardless of cause; the phase attribution ignores which phase changed the subject; or each re-run piles up duplicate fixes.

### C10 [core] — Milestone close is refused unless a full check passed on the current tip and no fix it opened is still open
- **Observe:** In the scratch project: (a) all phases accepted, no full check run — `ac milestone complete` exits non-zero naming the full-check command; (b) after a failing check with open fixes (C9) — refused, naming the open fixes; (c) after the fixes are resolved and a check passes at HEAD — succeeds (try on a copy so the earlier states can be replayed); (d) after a passing check, add one commit and try again — refused because the check is not for the current tip. Also try `/astro-complete-milestone`'s underlying verb path. Files: `bin/ac.mjs`, `lib/milestone.mjs`, `commands/astro-complete-milestone.md`.
- **Fails if:** a milestone closes without a passing check, with an open check-created fix, or on a tip newer than the passing check; or the refusal is only prose in the command and `ac milestone complete` itself lets it through.

### C11 [core] — The full check tries to repair the fixes it opened with an agent, bounded per fix (default 2 attempts), and ends with a report of what was fixed and what is still open
- **Observe:** Read the full-check orchestration (the command/workflow that runs it, e.g. `commands/astro-verify-milestone.md` and its workflow script) and drive its deterministic parts with `ac` in a scratch project: after a failing check with two fixes, simulate repair rounds in which one fix's failure is resolved by a commit and the other's never is. Expected: repair is attempted for each open fix the check created, the unresolvable fix gets no more than 2 attempts (default, from config), each attempt re-runs that fix's failing check, and the final report lists the first as fixed and the second as still open, then re-runs/requires the full check before close. The attempt limit is read from a setting with default 2. Files: `bin/ac.mjs`, `lib/milestone.mjs`, `workflows/`, `commands/`.
- **Fails if:** no repair is attempted after a failing check; attempts are unbounded or the bound is not 2 by default; a fix is reported fixed without its failing check passing again; or the run ends without the fixed/still-open report.

### C12 [edge] — When the last phase of a milestone is accepted, or close is attempted without a passing full check, astro-code proposes the full check in one line with its command
- **Observe:** In a fast-mode scratch project, accept the last pending phase of the milestone with `ac phase accept <phase> --agent test`; then run `ac milestone complete` without a check. Expected: the accept output (and `commands/astro-accept.md` / `commands/astro-complete-milestone.md` step text) proposes running the full check with the exact command in one line; accepting a non-last phase does not propose it. Files: `bin/ac.mjs`, `lib/phase.mjs`, `commands/astro-accept.md`, `commands/astro-complete-milestone.md`.
- **Fails if:** no proposal appears at last-phase accept or at a blocked close, the proposal starts the check automatically, or it appears after every accept.

### C13 [edge] — Release notes cut by astro-code mark fast-verified phases still pending a full check
- **Observe:** In a fast-mode scratch project with one fast-verified, accepted phase and no full check, run the release path that produces notes (`ac flow release` with a dry-run or local-only remote, as `MANUAL.md` documents). Expected: the produced notes name that phase as "full check pending"; after a passing full check on the tip, the notes do not. Files: `lib/flow.mjs`, `bin/ac.mjs`.
- **Fails if:** release notes list the phase as if fully checked while its full check is pending.

### C14 [edge] — Phases already fully verified before the change count as fully checked; nothing is re-run retroactively
- **Observe:** In a scratch project, record a phase as verified through a full-suite verdict (per-phase mode, or a verdict saved before fast mode existed), then switch to default fast mode. Run `ac status` and the full check. Expected: that phase carries no "full check pending" marker; the full check still runs the suite and that phase's `Cheap:` lines but does not re-verify the phase or reopen its state. Files: `lib/verdict.mjs`, `lib/status.mjs`, `lib/milestone.mjs`.
- **Fails if:** previously fully verified phases are shown as pending, or their verified/accepted status is reset by the change.

### C15 [edge] — The setting, fast mode, the milestone full check and the close gate are documented for users
- **Observe:** Read `MANUAL.md` and `commands/astro-config.md`: they name the setting and its values with the default (fast/milestone), say what a phase verify runs in each mode (including "no linked tests"), name the full-check command, what it runs, how failures become fixes and are repaired, and that milestone close needs a passing check on the current tip. Every command named there exists in `ac help` output (`node bin/ac.mjs help`).
- **Fails if:** a user reading the docs cannot find how to restore the full suite per phase or how to run the milestone full check, or the docs name a setting/command the CLI does not accept.

### C16 [suite] [core] — The whole test suite passes with the change, including new tests for the targeted selection, the fast PASS gate, the full check and the close gate
- **Observe:** `npm test` (runs `node scripts/test.mjs`) exits 0 on the verified commit; the engine changes in `lib/` have node:test coverage for target selection (C3), no-linked-tests (C4), the fast PASS gate (C5), the full check and fix attribution (C8, C9) and the close gate (C10).
- **Fails if:** any test fails or the suite errors on load, or the new engine behaviour ships with no test exercising it.
