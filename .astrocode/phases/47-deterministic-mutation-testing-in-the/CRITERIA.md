# Phase 47 — Success criteria (pre-registered, plan-blind)

> Derived from the phase goal, CONTEXT.md (D1–D4, Scope) and the canon (ADR-001, ADR-021,
> ADR-079, ADR-083). Every criterion is checked by driving the real `ac` CLI
> (`node /Users/buu/Development/astro-code/bin/ac.mjs`) against scratch projects under
> `mktemp -d`. No real Stryker, Gremlins or mutmut is needed or allowed: the tool is
> faked by a stub executable placed where the project's own tool would be found (on
> `PATH`, or `node_modules/.bin` for JS). The stub writes a known report in the tool's
> real format and logs the arguments, working directory and environment it received.
> A "phase" in a scratch project means one created through `ac` (init, phase add) whose
> work is in ADR-017-stamped commits `(phase NN tK)`.

### C1 — `ac mutate <phase>` turns the tool's report into one fixed, complete, repeatable mutant list
- **Observe:** In a scratch JS/TS project (`package.json`, git repo, a phase whose stamped commits change `src/a.mjs`), put a fake Stryker on the lookup path that writes a Stryker JSON report (mutation-testing-report schema) containing a known set of mutants, at least one each of `Killed`, `Survived`, `Timeout`, `NoCoverage` and `RuntimeError`/`CompileError`. Run `ac mutate <phase> --json` twice, then once without `--json`. Expected: the JSON lists **every** mutant in the fixture, each with file, line, mutator and a status from exactly `killed | survived | timeout | no-coverage | error`, mapped correctly. The counts per status match the fixture. Both JSON runs are identical apart from timestamps or durations. The output names the tool and why it was picked (for example "package.json → Stryker"). The human output reports the same counts and lists the same survivors.
- **Fails if:** a mutant from the report is missing or duplicated; a status is mapped wrong (for example `NoCoverage` counted as killed, or `Timeout` as survived); file, line or mutator is missing; two runs over the same report give different lists or counts; the human and JSON outputs disagree; the output does not say which tool was picked or why.

### C2 — The run is scoped to the files the phase changed, never the whole repo or another phase's files
- **Observe:** In the C1 scratch project, add a second phase whose stamped commits change `src/b.mjs`, and leave an unrelated file `src/c.mjs` untouched by any phase. Run `ac mutate <first-phase>` and inspect what the stub logged (argv, config it was given, or the files it was told to mutate). Expected: the tool was told to mutate only `src/a.mjs` (the first phase's changed source files), and the output names the scoped files. Repeat for a Go project (fake `gremlins`) and a Python project (fake `mutmut`). Each tool receives only that phase's changed files.
- **Fails if:** the stub was asked to mutate `src/b.mjs`, `src/c.mjs` or the whole project; no scope was passed at all, so the tool falls back to its default of the whole project; the scope comes from the working-tree diff or the branch-vs-base diff and so picks up another phase's commits; for any of the three ecosystems, the changed files are not passed explicitly when that tool has no diff mode.

### C3 — The tool is detected per ecosystem, an explicit config override wins, and each tool's report is parsed
- **Observe:** Make three scratch projects: `go.mod` with a fake `gremlins` that emits a Gremlins JSON report, a Python project (`pyproject.toml`, `setup.py` or `requirements.txt`) with a fake `mutmut` that exposes its results in mutmut's real results format, and the JS project from C1. Run `ac mutate <phase> --json` in each. Then set the explicit tool override in the project's astro-code config to a different tool and run again. Expected: Go picks Gremlins, Python picks mutmut and JS picks Stryker. Each output states the tool and the manifest that chose it. Each fixture's mutants and statuses come back complete and correct, as in C1. With the override set, the overridden tool is used and the output says the choice came from config.
- **Fails if:** any ecosystem picks the wrong tool or none; the Gremlins or mutmut fixture parses to an empty, partial or mis-statused list while Stryker works; the override is ignored, or merged with detection so detection still decides; the output does not say why the tool was chosen.

### C4 — A time cap bounds the run, defaults to 10 minutes, and a capped run never reads as "all killed"
- **Observe:** (a) With no cap configured, `ac mutate <phase> --json` (fake tool) reports a cap of 10 minutes (600 s). (b) Set a short cap in config, for example 2 s, and use a fake tool that kills a few mutants and then sleeps for 60 s, spawning a child that also sleeps. Time `ac mutate <phase> --json`. Expected: it returns within the cap plus a small margin. The result marks the run as capped, lists the mutants that were not run, and does not report "all mutants killed" or a passing state. After it returns, neither the stub nor its child is still running (`ps`). (c) Rerun with every fixture mutant `Timeout` and the run not capped. Timeouts count as killed.
- **Fails if:** the default is not 10 minutes, or a configured cap is ignored; the command waits for the stub to finish; the stub or its child keeps running after the cap; a capped run says "all killed", or presents itself the same way as a complete run; the mutants not run are not listed; timeouts are counted as survivors.

### C5 — With no tool installed, it suggests the exact install command, installs nothing, never prompts, and states the AI-mutant fallback reason
- **Observe:** In a JS, a Go and a Python scratch project with no mutation tool available, put logging stubs for `npm`, `npx`, `pip`, `pip3`, `go` and `yarn`/`pnpm` on `PATH`. Each stub records that it was called and exits non-zero. Snapshot the dependency manifests, the lockfiles, `node_modules` and `git status --porcelain`. Run `ac mutate --check` and `ac mutate <phase>` with `</dev/null` under `timeout 60`. Expected: each project prints its own exact command: `npm i -D @stryker-mutator/core` (JS/TS), `go install github.com/go-gremlins/gremlins/cmd/gremlins@latest` (Go) and `pip install mutmut` (Python). Both commands finish without waiting for input. The `--json` result says no tool is available and that AI-invented mutants are the fallback, with the reason. No install stub was invoked to install anything, and the manifests, lockfiles and `node_modules` are byte-identical afterwards.
- **Fails if:** an install command is wrong or uses another ecosystem's tool; any package manager is invoked to install; a manifest, lockfile or dependency directory changes; the command blocks on stdin or hits the timeout; it exits as a hard error with no fallback reason. (A nonzero exit is acceptable only if the result still states the fallback and why.)

### C6 — The full install suggestion appears once per project per tool, and is remembered across runs and after a dismissal
- **Observe:** In a fresh JS scratch project with no tool, run the invocation verification uses (`ac mutate <phase>`, human and `--json`) three times as separate processes. Expected: the first run shows the full suggestion with the install command. Later runs do not repeat it and show at most a one-line reminder, such as "mutation tool not installed — AI mutants used". In a second fresh project, dismiss the suggestion through the dismissal path the CLI documents, then run `ac mutate <phase>`. The full suggestion does not appear. In a Go project on the same machine, Gremlins gets its own first-time suggestion, because the memory is per project per tool and not global. In a fresh clone or copy of the first project whose memory was never written, the suggestion appears once again. The memory must survive between separate `ac` processes. An explicit `ac mutate --check` may always print it, because the user asked.
- **Fails if:** the full suggestion repeats on the second or third verify-path run; the reminder is longer than one line, or repeats the full install block; a dismissal is not remembered; one tool's "shown" state suppresses a different tool's first suggestion, or one project's state suppresses another project's; the memory lives only in process memory and resets on every invocation.

### C7 — Only an explicit `ac mutate setup` writes tool config; running or checking never changes the project
- **Observe:** In a JS scratch project with a fake tool, record `git status --porcelain --untracked-files=all` and a hash of every file outside `.astrocode/`. Run `ac mutate --check` and `ac mutate <phase>`, then hash again. Nothing outside astro-code's own state should have changed, and no tool config file should appear. Then run `ac mutate setup`. A minimal config for the detected tool appears and parses (load or parse it with node). It is scoped to the project's sources, and a following `ac mutate <phase>` runs with it (the stub's log shows it read that config). Repeat `setup` for the Go and Python projects. The dependency sections of the manifests stay unchanged throughout.
- **Fails if:** `check` or a run writes a tool config, edits a manifest or adds dependencies; `setup` installs anything or edits dependency lists; `setup` writes a config that does not parse or that the tool would not read; setup also happens implicitly on the first run or verify.

### C8 — The verdict records reproducible mutation evidence, and `ac verdict record` keeps it
- **Observe:** Build a verdict for a scratch phase with one test-strength criterion. Give it a mutation evidence block holding the tool, its version, the exact command run, the counts per status, the cap, whether the run was capped, and every survivor with its triage: `test-gap`, or `equivalent` plus a one-line justification. Record it with `ac verdict record`, then read back the verdict saved in the phase folder. Expected: every field is present and unchanged. Re-running the recorded command (or `ac mutate <phase> --json`) against the same fake tool gives the same counts and the same survivor list. Recording a no-tool fallback verdict instead keeps the stated reason, for example "mutation tool not installed — AI mutants used".
- **Fails if:** `ac verdict record` refuses the evidence block, or silently drops or flattens it; tool, version, command, counts or survivor triage is missing from the saved verdict; the recorded command cannot reproduce the recorded counts; the fallback reason is lost.

### C9 — A verdict cannot pass a test-strength criterion that still has a test-gap or an unjustified survivor
- **Observe:** Feed `ac verdict record` three variants of the C8 verdict, each marking the test-strength criterion PASS: (a) one survivor triaged `test-gap`; (b) one survivor triaged `equivalent` with an empty justification; (c) evidence listing fewer triaged survivors than its own survivor count, with one survivor left untriaged. Then record (d): every survivor justified as equivalent, and the run not capped. Also record (e): a capped run whose criterion is marked PASS because "all killed". Expected: (a), (b), (c) and (e) are refused, or saved with that criterion and the phase not passed, and the output names the offending survivor or the capped run. (d) is saved as passed, with each one-line justification kept and visible.
- **Fails if:** any of (a), (b), (c) or (e) is saved as a passing criterion or a passed phase; (d) is refused; a justification is dropped from the saved verdict.

### C10 — The verifier and criteria-author instructions put this into practice, and agree on how a test-strength criterion is marked
- **Observe:** Read the installed or rendered instructions for the verifier agent and the verify command, and for the criteria author. Expected: the verifier is told to run `ac mutate <phase> --json` for a test-strength criterion, to triage only the survivors (test gap fails the criterion, equivalent passes with a one-line justification), to count timeouts as killed, to treat a capped run as never "all killed", to record the evidence through `ac verdict record`, and to use AI-invented mutants only when no tool is available, with the reason stated. Criteria without the test-strength marker must not trigger mutation. The criteria author is told how to write a test-strength criterion, and the marker it is told to write is the same marker the verifier and `ac mutate` look for. Check this by writing a CRITERIA.md that follows the author guidance word for word, then confirming that whatever `ac mutate` or the verify path uses to find test-strength criteria recognises it.
- **Fails if:** the verifier is still told to invent mutants by hand when a tool is present, or to judge killed mutants; mutation is told to run on every verify; the author's marker and the marker the verifier or `ac mutate` look for differ, so a correctly written criterion is never recognised; the fallback is allowed without stating a reason.

### C11 — The suite proves all of this without any mutation tool installed, and astro-code stays dependency-free
- **Observe:** Run the full suite (`node --test` over `tests/`, the same as the project's test script) with a `PATH` that does not contain `stryker`, `gremlins` or `mutmut`. Then read `package.json`. Expected: the suite passes, and includes tests that drive `ac mutate` through fixture reports or stub binaries for all three tools, the cap, the no-tool path and the suggestion memory. `package.json` still declares no `dependencies` and no `devDependencies` (ADR-001).
- **Fails if:** any test fails or is skipped because a real mutation tool is missing; a dependency or dev dependency was added; the new behaviour is tested only against prompt strings and never by running the command.

### C12 — A user can find out how to use it from `ac help` and the manual
- **Observe:** Run `ac help`, then read the manual section and the CHANGELOG entry that cover mutation testing. Expected: `ac help` lists `ac mutate <phase>` with `--check`, `--json` and `setup`. From the manual, a user can learn: which tool each language uses, the exact install commands, how to change the cap and the tool override, how to dismiss the install suggestion and where that memory is kept (committed or local, and why), and that astro-code never installs a tool. The CHANGELOG records the feature.
- **Fails if:** `ac help` does not mention `ac mutate`, or omits one of its forms; the manual gives install commands that differ from what the CLI prints; the manual does not explain how to dismiss the suggestion, where the memory lives, or how to set the cap and override.
