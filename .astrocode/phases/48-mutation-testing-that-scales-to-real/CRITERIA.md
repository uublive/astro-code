# Phase 48 — success criteria (pre-registered, plan-blind)

Shared harness for C1–C9: a scratch git repo under `mkdtemp`, initialised with `ac init`, with
a phase whose work lands as ADR-017 stamped commits (`(phase NN tK)`), plus unstamped commits
before and after it. Each mutation tool is replaced on `PATH` by a stub executable that
(a) appends its full argv, cwd and relevant env to a record file, (b) answers `--version` like the
real tool (Stryker 10.x, Gremlins 0.6.x, mutmut 2.4.x / 3.8.x), and (c) writes a report in the real
tool's shape (the repo's own fixture reports may be reused, or hand-written equivalents). The
verifier judges each criterion from what the stub was asked to do and from what `ac mutate`
prints / writes, never from reading the implementation.

### C1 — For Stryker, `ac mutate <phase>` mutates only the line ranges the phase's stamped commits changed
- **Observe:** JS scratch repo with `src/big.js` (≈300 lines) and `src/other.js`. Before the phase, an unstamped commit edits `src/big.js` lines 200–210; the phase's stamped commits change only lines 40–45 of `src/big.js` (plus a remediate-stamped commit changing lines 90–91); a later unstamped commit edits `src/other.js`. Run `ac mutate <phase> --json` with the Stryker stub. The recorded invocation targets `src/big.js` by line range(s) covering exactly 40–45 and 90–91 (e.g. `src/big.js:40-45`, `src/big.js:90-91`), and nothing else; the JSON/human result states the scope that applied (changed lines) and why.
- **Fails if:** the stub is handed the whole file (`src/big.js` with no range), lines 200–210 or `src/other.js` appear in the scope, the remediate-stamped lines are missed, or the result does not say which scope was used.

### C2 — For Gremlins, `ac mutate <phase>` uses Gremlins' own diff mode against the phase's base commit
- **Observe:** Go scratch module with two packages; the phase's stamped commits change a few lines in one package, an unstamped commit after the phase changes the other. Run `ac mutate <phase> --json` with the Gremlins stub. The recorded `gremlins unleash` invocation uses its diff mode (`--diff`) referencing the commit immediately before the phase's first stamped commit (verify with `git rev-parse <first-stamped>^`), and does not enumerate every other file as an exclusion. Survivors in the result are filtered to the phase's changed lines.
- **Fails if:** no diff mode is used, the base is HEAD~1 / the branch point / anything other than the phase's base, the scope is built by excluding all other files, or survivors from the post-phase commit's lines are reported.

### C3 — For mutmut 3, only the functions whose bodies hold changed lines are mutated; mutmut 2 states what it narrowed to
- **Observe:** Python scratch project with `pkg/mod.py` defining functions `a`, `b`, `c` (plus a class method `K.m`). The phase's stamped commits change one line inside `b` and one inside `K.m`. With a mutmut 3.8 stub, run `ac mutate <phase> --json`: the recorded `mutmut run` invocation selects mutants by name for `b` and `K.m` only (mutant-name globs or equivalent native selection), never `a` or `c`. Repeat with a mutmut 2.4 stub: the run uses the closest supported narrowing and the result states which mechanism applied (function-level, or file-level with the reason).
- **Fails if:** mutmut 3 is run over the whole module or project, `a`/`c` are selected, a changed method is missed, or mutmut 2 silently falls back to whole-file scope without the result saying so.

### C4 — A project setting can add or skip files, and the result says which scope applied and why
- **Observe:** In the C1 repo, set the documented project setting(s) (e.g. `mutation.exclude` naming `src/big.js`, then `mutation.files` adding an untouched `src/extra.js`) through the documented interface, rerun `ac mutate <phase> --json` each time. The stub's recorded targets drop the excluded file / include the added one, and the result names the scope source (changed lines vs project setting) and the reason. Do the same for one of Gremlins/mutmut.
- **Fails if:** the setting is ignored, applies to one tool only, or the result reports the same scope description regardless of which source decided it.

### C5 — By default the run uses only the tests the phase's commits added or changed; an override names others; no touched tests means a stated fallback to the full suite
- **Observe:** For each tool (Stryker, Gremlins, mutmut 3): (a) the phase's stamped commits change `tests/test_b.*` (Go: a `_test.go` in the changed package) while other test files exist untouched → the stub's recorded invocation restricts the test run natively (Stryker test-file/runner options, `go test` package/run filters through Gremlins, mutmut 3 test selection / pytest args) to the phase's tests only, and the result names those tests; (b) set the documented tests override (project or phase level, e.g. `mutation.tests`) to another test file → that file is what the tool is told to run, and the result names it; (c) a phase whose commits touch no test file → the result says the phase touched no tests and that the full suite is used, and the stub receives no test restriction.
- **Fails if:** the full suite runs while phase tests exist, untouched test files are included by default, the override is ignored, the fallback happens silently, or the result does not name the tests used.

### C6 — The time cap is settable per phase and a capped run says exactly which step it was in, how far it got, and which key to raise
- **Observe:** With a stub whose initial (baseline) test run sleeps 30 s, set the project cap low (e.g. `mutation.cap_seconds` = 5) and run `ac mutate <phase> --json`: it returns within a few seconds of the cap, the stub process is gone afterwards (`ps`), and the result names the step ("initial test run" or equivalent), the number of mutants tested (0), and the setting key(s) to raise (project and phase level). Repeat with a stub that is mid-way through mutants at the cap: the result names that step and the tested/total counts. Then raise the cap for this phase only, through the documented phase-level setting (no hand edit of `roadmap.json`/`state.json`), and rerun: the run completes, while another phase still gets the project cap. With no setting at all, the effective cap reported is 600 s.
- **Fails if:** a capped run reports only "incomplete"/"timeout" without the step and counts, it overruns the cap materially or leaves the tool running, the phase-level cap is ignored or leaks to other phases, setting it requires hand-editing roadmap/state JSON, or the default is not 600 s.

### C7 — The tool's log is kept locally beside the phase's run, named in the result, never committed, and replaced on the next run of the same phase
- **Observe:** Run `ac mutate <phase> --json` with a stub that prints a unique marker to stdout/stderr. The result gives a log path under `.astrocode/.local/`; that file contains the marker; `git status --porcelain` stays clean of it (`git check-ignore` matches). Rerun with a different marker: the same phase's log now holds only the new marker (no accumulation, no second file left behind), and a run for a different phase does not overwrite it. Nothing is written to the system temp dir as the only copy.
- **Fails if:** the log lives only in a temp folder, the path is not reported, the log is committable/untracked-visible, or reruns append/accumulate instead of replacing.

### C8 — The result lists every survivor in full but summarises killed / timed-out / not-run mutants as per-file counts, with the complete list in a local file whose path it gives
- **Observe:** Feed a fixture report with ≥ 5,000 in-scope mutants across 3 files, of which 4 survived (and some timeout / not-run). Run `ac mutate <phase> --json` and the human form. Each of the 4 survivors appears individually with file, line and the mutation; killed, timeout and not-run appear only as per-file counts (no per-mutant entries); the counts sum to the report's totals. The JSON stays small (well under 100 KB, versus multi-MB for a per-mutant dump). The result gives a local file path; that file lists all ≥ 5,000 mutants with their status. Survivors outside the phase's scope are not listed as survivors.
- **Fails if:** any survivor is dropped or truncated, killed/timeout/not-run mutants are listed individually in the human or JSON output, counts disagree with the report, the full-list file is missing / incomplete / unreported, or the JSON size scales with total mutants.

### C9 — mutmut 3 mutants are reported at their real source line, not line 0
- **Observe:** Using a mutmut 3 fixture where survivors are known by mutant name only (e.g. `pkg.mod.x_b__mutmut_3`) with their diffs, run `ac mutate <phase> --json`. Each reported survivor carries a line > 0 that is the line in `pkg/mod.py` where the mutated code sits (open the file at that line: the original expression the mutant changed is there), and that line falls inside the phase's changed function. Filtering to scope uses those real lines.
- **Fails if:** any mutmut 3 mutant is reported at line 0, all mutants of a function share the `def` line, or line mapping is wrong for a mutant that is not the first in its function.

### C10 — The install hint matches how the project manages its environment, and `ac mutate` never installs anything
- **Observe:** With no tool on `PATH`, run `ac mutate <phase>` in scratch projects shaped as: (a) Python with a `.venv` that has no pip (uv-style) → the hint is the `uv pip install --python .venv/bin/python mutmut` form; (b) `pnpm-lock.yaml` → `pnpm add -D …`; (c) `yarn.lock` → `yarn add -D …`; (d) `package-lock.json` or no lockfile → `npm install -D …` form; (e) Go → the existing Go hint; (f) a project whose environment pins versions (e.g. a lockfile/requirements pin for the tool's ecosystem) → an added warning that an install may change nothing. Before/after each run, the lockfiles, `node_modules`, `.venv` and `go.mod`/`go.sum` are byte-identical.
- **Fails if:** a pip-less venv gets `pip install mutmut`, a pnpm/yarn project gets an npm command, the pin warning is missing, or any run modifies the environment.

### C11 — An installed mutmut 3 that crashes on `--version` because it lacks configuration is reported as installed but not configured, pointing at `ac mutate setup`
- **Observe:** Put a mutmut stub on `PATH` whose `--version` exits non-zero with mutmut 3's "cannot find source folder" style error. Run `ac mutate <phase>` (human and `--json`). It reports mutmut as installed but not configured and names `ac mutate setup`; it gives no install hint and does not say "not installed".
- **Fails if:** the result says the tool is missing, prints an install command, or crashes.

### C12 — `ac mutate setup` writes settings the installed tool version actually accepts
- **Observe:** In a Python scratch project with a mutmut 3.8 stub, run `ac mutate setup`; the written mutmut configuration uses the current 3.x keys (e.g. `source_paths`, `pytest_add_cli_args_test_selection`) pointing at the project's real source and test folders, and contains no key mutmut 3 deprecated or ignores. With a mutmut 2.4 stub in a fresh project, the written configuration uses keys valid for 2.x. Re-running setup does not duplicate or corrupt existing settings. Where a real mutmut 3 is available (container or via `host`), `mutmut --version` and a run on that project start without config errors after setup.
- **Fails if:** 3.x gets deprecated 2.x keys (or vice versa), paths do not match the project layout, or a second setup run duplicates entries.

### C13 — When a mutation tool is installed, the verifier is directed to run `ac mutate` wherever it would hand-make mutants; only `[mutation]`-tagged criteria get the code pass bar
- **Observe:** Read the installed verifier role and `/astro-verify` instructions as a whole: with a tool installed they direct running `ac mutate` and triaging its survivors for any criterion (tagged or untagged) whose check would involve making broken versions of the code, forbid hand-invented mutants in that case, and keep hand-made mutants only as the no-tool fallback; no remaining instruction contradicts this (e.g. hand-mutating for untagged criteria when a tool exists). Then exercise `ac verdict record` in a scratch project: an untagged criterion recorded PASS with mutation evidence as supporting evidence (or without it) is accepted; a `[mutation]`-tagged criterion recorded PASS without valid tool evidence is still refused, exactly as in phase 47.
- **Fails if:** any verifier instruction still permits hand-made mutants when a tool is installed, untagged use is turned into a code gate, or the `[mutation]` gate behaviour changes.

### C14 — The invocations `ac mutate` builds are accepted by the real tools' current versions
- **Observe:** For each of Stryker 10, Gremlins 0.6 and mutmut 3.8 (and 2.4) that is available in the container or on the host via `host` (no network installs): run `ac mutate <phase> --json` on a tiny scratch project of that language with a phase changing a few lines. The tool runs to completion with no unknown-flag/option error, the result shows the narrowed scope, the phase's tests, survivors at real lines, the log path and full-list path. For any tool not available, compare every flag `ac mutate` passes (from a stub record) with that tool's documented CLI in the repo's checked fixtures/help captures and note the tool as not run.
- **Fails if:** a real tool rejects a flag or config key `ac mutate` produces, ignores the scope/test selection (mutating outside it or running the whole suite), or produces a report `ac mutate` cannot parse.
