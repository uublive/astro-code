# Phase 49 — Survivor triage support — pre-registered criteria

> Plan-blind. Derived from the phase goal, CONTEXT.md (D1–D6, folded-in debt) and canon
> (ADR-083/084/085, ADR-079). "Fixture project" below means a throwaway git repo the verifier
> builds under its scratch dir, registered as an astro-code phase whose change set produces
> mutants, run against the real tools installed in this container (Stryker 10, Gremlins 0.6,
> mutmut 2.4/3.8) unless a criterion says a stub tool is acceptable. "Record a judgement" means
> whatever interface the finished system offers a person or the verifier for it (a command, or
> editing the per-phase survivors file by hand as a reviewer would) — the criteria do not care
> which.

### C1 — Survivors come back grouped by function and mutation kind, with text-only changes in a group of their own, in both human and JSON output
- **Observe:** In a fixture project whose phase change leaves survivors in at least two functions, of at least two mutation kinds, including at least two survivors that only change a string/message literal (an error string, a log line), run `ac mutate <n>` and `ac mutate <n> --json`. In both outputs every survivor appears under exactly one group keyed by function + mutation kind; every text-only (string/message literal) survivor is in a text-only group and in no logic group; per-group counts sum to the total survivor count.
- **Fails if:** survivors are a flat list in either output; a string-literal survivor is grouped with logic mutants of its function; the JSON carries no machine-readable grouping (only the human text groups); a survivor is missing, duplicated across groups, or the group counts do not add up to the survivor total.

### C2 — One note can cover a whole text-only group, but only the survivors it actually covers; nothing is auto-marked equivalent
- **Observe:** On the C1 fixture, before any judgement is recorded, confirm no survivor (text-only included) is reported as judged/equivalent. Record one `equivalent` judgement with a one-line justification for the text-only group; re-run `ac mutate <n> --json`: every survivor that was in that group is now judged, logic survivors stay open. Then add a new string-literal change to the phase code that produces a new text-only survivor and re-run: the new survivor is open (untriaged), not inherited from the group note. Separately, record `equivalent` with an empty justification for some survivor and confirm it is refused or still reported open.
- **Fails if:** text-only survivors are counted as equivalent with no recorded note; the group note leaves some of its members open; a survivor that did not exist when the group note was written is covered by it; an `equivalent` with no justification counts as judged.

### C3 — Judgements live in a committed per-phase file and carry over to the next run, including in a teammate's fresh clone
- **Observe:** In a fixture project, run `ac mutate <n>`, record one `equivalent` (with justification) and one `test-gap` judgement, and confirm the judgements landed inside the phase folder in a file git does not ignore (`git check-ignore <that path>` exits non-zero; `git status` shows it as a change to commit). Commit, then `git clone` the fixture to a new dir and run `ac mutate <n> --json` there on unchanged code: the two survivors carry their recorded judgement (kind and justification text), the open count equals the survivor total minus the judged ones, and the human output distinguishes carried-over judgements from survivors still needing a verdict.
- **Fails if:** a re-run on unchanged code shows previously judged survivors as untriaged again; judgements live only in a gitignored, home-dir or temp location (lost in the clone); the clone's run disagrees with the original's judgements; the output does not separate judged from still-open survivors.

### C4 — A judgement follows its mutant, not its line number: a changed mutant re-opens, an unrelated line shift does not
- **Observe:** In the C3 fixture with judged survivors, (a) insert unrelated lines above a judged survivor's function so its line number shifts, re-run `ac mutate <n> --json`: the judgement still applies to that survivor. (b) Edit the code on the judged survivor's mutated line so the mutant's original/replacement text changes (or the mutant disappears and a different one appears there), re-run: that survivor is open again while other judged survivors keep their judgements.
- **Fails if:** a pure line shift re-opens judged survivors (matching by line number alone); editing the mutated code leaves the stale judgement attached; one changed mutant re-opens every judgement in the file.

### C5 — `ac mutate <n> --survivors` re-tests only the open survivors, on each supported tool, and Gremlins says how it narrowed
- **Observe:** For a fixture per tool (JS/TS with Stryker, Python with mutmut, Go with Gremlins), run a full `ac mutate <n> --json` that yields some killed mutants and some survivors; judge one survivor `equivalent`, one `test-gap`, leave at least one untriaged. Run `ac mutate <n> --survivors --json`: the mutants actually executed (from the result's per-mutant list and the tool's own report/output) are exactly the `test-gap` + untriaged ones — no killed mutant and no `equivalent`-judged mutant is re-run — and the run takes measurably fewer mutant executions than the full run. For Gremlins the output states the narrowing method it used (and that it is narrower-than-ideal if it is).
- **Fails if:** `--survivors` re-runs the full mutant set or any already-killed mutant on any of the three tools; it re-runs `equivalent`-judged mutants; it silently skips an open survivor; the flag is rejected or ignored by any tool path; Gremlins falls back to a full run without saying so.

### C6 — A `--survivors` run is never the recorded verdict: the bar stays bound to the last full run
- **Observe:** After C5's `--survivors` run kills a previously open survivor (fix a test so it does), confirm `ac mutate <n>` output may show the combined picture but labels it as a partial re-run on top of the last full run. Then attempt `ac verdict record` with a passing test-strength criterion bound to the `--survivors` run (or with no full run since the code changed): it is refused. After a fresh full `ac mutate <n>` that leaves every survivor killed or justified, the same verdict is accepted.
- **Fails if:** `ac verdict record` accepts a passing test-strength criterion whose kept-run evidence is a `--survivors` (partial) run; the combined display is indistinguishable from a full run; a full run is no longer what the verdict binds to (ADR-083 kept-run binding weakened).

### C7 — Flaky tests are caught before mutating: named, and their kills re-checked or not counted, saying which
- **Observe:** In a fixture project add, to the phase's tests, one test that fails on alternate runs on unchanged code (e.g. toggles a counter file in the scratch dir) alongside stable tests. Run `ac mutate <n> --json` (and the human form): before mutation results, the output names that test as flaky; kills attributed to it are either re-checked or excluded from the kill count, and the result states which of the two happened. Repeat on the same fixture with the flaky test removed: no test is reported flaky and the kill count is not reduced.
- **Fails if:** the flaky test is not named; its kills are counted as kills with no re-check and no statement; the result does not say whether kills were re-checked or discounted; a stable suite is reported flaky or has kills discounted.

### C8 — The double test run on unchanged code spends the same single cap, and a cap hit there is named
- **Observe:** On a fixture whose phase tests take long enough that two runs exceed a small cap, run `ac mutate <n> --json` with that cap (via whatever cap setting the tool already honours) and time it: wall time stays within the cap plus a small startup margin, the result is marked capped, and it names the flaky-check / test-run-twice step as where the cap was hit. With a generous cap the same fixture completes the check and mutates.
- **Fails if:** the pre-mutation test runs are outside the budget (wall time exceeds the cap materially, or the cap restarts for mutation); a cap hit during that step is reported as a clean or uncapped run, or without naming the step; the step is silently skipped to fit the cap.

### C9 — An untagged criterion the verifier marks test-strength gets the full code-checked bar from `ac verdict record`
- **Observe:** In a fixture phase whose CRITERIA.md has an untagged criterion (no `[mutation]`, unedited, worded like Waupaca phase 26's), record verdicts through `ac verdict record`: (a) criterion passed + marked test-strength, kept full run has an open survivor (untriaged or `test-gap`) → refused; (b) same, bound to a run other than the kept run → refused; (c) same, every survivor killed or justified `equivalent` → accepted. Repeat (a)–(c) with a `[mutation]`-tagged criterion: identical outcomes to before this phase (tag still works unchanged).
- **Fails if:** `ac verdict record` accepts (a) or (b) for the marked untagged criterion; it requires editing CRITERIA.md (adding a tag) to apply the bar; `[mutation]`-tagged criteria behave differently than before.

### C10 — The test-strength mark is sticky per phase: a later verdict cannot drop it, and it survives a fresh clone
- **Observe:** After C9(c) records criterion Cx as test-strength, record a second verdict for the same phase that passes Cx WITHOUT the test-strength mark while the kept run has an open survivor (or no tool evidence): it is refused (or the full bar is applied anyway and it fails). Commit and `git clone`; repeat the attempt in the clone: still refused. In a different phase of the same fixture, a criterion with the same id Cx is not affected. Confirm `.astrocode/roadmap.json` was changed only through `ac` (no hand edit needed to set or keep the mark).
- **Fails if:** omitting the mark in a later verdict lets Cx pass on verifier say-so; the mark is lost on a fresh clone or a re-run of `/astro-verify`; the mark leaks to another phase's same-numbered criterion; keeping the mark requires hand-editing roadmap.json/state.json.

### C11 — The verifier and criteria-author instructions match the new bar: the tool's result is the bar for every test-strength criterion, and the verifier starts from recorded judgements
- **Observe:** Read the installed verifier agent, `/astro-verify` command and criteria-author instructions as a verifier/author would follow them: they direct the verifier to mark a criterion test-strength in the verdict whenever it uses `ac mutate` for it, tagged or not; to start from the phase's recorded judgements and judge only new or re-opened survivors; to use `--survivors` for fix rounds but bind the verdict to a full run; and to treat a named flaky test per the tool's result.
- **Fails if:** any of them still says only `[mutation]`-tagged criteria get the code-checked bar (ADR-084's tag-only gate, now amended by ADR-085); the verifier is told to re-judge every survivor each run; nothing tells the verifier to declare the test-strength mark.

### C12 — A Gremlins built with `go install` (reports `version dev`) gets its real module version into the evidence
- **Observe:** Run `ac mutate <n> --json` on a Go fixture using the container's Gremlins. If `gremlins --version` prints `dev` / no version, the evidence's tool version is non-null and equals the module version shown by `go version -m "$(command -v gremlins)"`. With a stub `gremlins` on PATH that does print a real version, that version is used.
- **Fails if:** tool version is `null`, `dev`, or empty for the go-installed binary; it disagrees with `go version -m`; a binary that reports a real version gets it overwritten.

### C13 — `/astro-verify`'s fallback line is worded from the fallback reason: it never claims AI mutants stood in when none were used
- **Observe:** For each fallback reason the mutation evidence can carry (at least: no tool installed; `mutation.exclude`; tool installed but no scope), produce the human verify-report line the system emits or prescribes for it (render it if the wording is produced in code; otherwise follow the `/astro-verify` instructions for that reason). Only the no-tool case says AI mutants stood in; the `mutation.exclude` and tool-installed-no-scope cases say no mutants were run and why.
- **Fails if:** any reason under which no AI mutants were used yields a line saying AI mutants stood in; the line ignores the reason and is one fixed sentence for all cases.

### C14 — The whole suite passes and the new behaviour is documented for a user
- **Observe:** Run `node --test` over the repo's tests (the project's normal test command): zero failures. Read MANUAL and CHANGELOG: a user can learn from them how to judge survivors and where judgements are kept, what re-opens a judgement, how `--survivors` works and that it is not the recorded verdict, the flaky-test check and that it shares the cap, and that any criterion the verifier uses the tool for gets the code-checked bar (sticky).
- **Fails if:** any test fails or the suite cannot be collected; MANUAL still describes the tag-only gate or omits the survivors file / `--survivors` / flaky check; CHANGELOG has no entry for this phase's user-visible changes.
